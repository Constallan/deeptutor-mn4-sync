# MarginNote 4 卡死诊断书

## 结论

采样确认卡死窗口内，MarginNote 主线程持续执行 JavaScript → Objective-C 桥接属性读取，路径包含对象包装、Core Data 查询和 SQLite 工作。结合修复前的同步循环，反复读取原生关系集合和整库收集不让出事件循环，是证据最强的原因。采样未提供 JavaScript 源码行号，不能直接证明具体哪一个 getter 占用了多少时间。网络等待不是本次采样中的首要阻塞点。

## 症状与范围

- 环境：MarginNote 4.4.6、macOS 27.0、Apple Silicon。
- 启用插件后出现长时间无响应；禁用插件后消失。
- 关闭当前学习集不停止全局定时同步，因为学习模式检查只控制工具栏显示。
- 用户数据规模约 20,434 个对象；修复前每次均扫描全部学习集。

## 采样证据

原始证据保存在本机、未纳入版本库的 `sampling/`：卡死期采样与未加载插件的基线采样。下列统计保留为可公开复核的脱敏摘要。

- 卡死期主线程 2,663/2,663 个样本均处于 `NSTimer → JSValue → drainMicrotasks`。
- 两个属性读取入口分支为 1,812 + 844 = 2,656 个样本，占主线程样本约 99.7%（卡死采样第 56、1724 行）；其下实际慢路径函数为 1,811 + 843 = 2,654。路径继续进入 Objective-C 回调、`NSInvocation`、Core Data fetch 和 SQLite；此比例不等于数据库本身占比。
- 基线主线程 2,400/2,403 个样本处于正常事件等待。
- 卡死期物理内存为 753.6 MB，峰值 884.2 MB；基线分别为 329.7 MB 和 415.7 MB。运行时长不同，因此内存差值只作佐证。

## 代码对应

修复前的 `collectAllObjects()` 在异步边界前调用 `db.allNotebooks()`，随后重复读取 `topic.notes`、`topic.documents` 和笔记属性。假设一个学习集含 20,434 条笔记，循环仅 `topic.notes` 就读取 40,870 次（一般公式为每学习集 2N + 2 次；20,434 个同步对象不一定全是笔记）。批量上传发生在完整收集之后，不能降低收集阶段的主线程阻塞或内存峰值。

修复前，20,434 个同步对象还会生成 41 个串行请求；全部结束后才等待 60 秒。这能解释为何同步可能持续很久，但采样本身不能量化完整同步所需时间。

## 已排除与待确认

- 已排除网络线程作为采样窗口内的直接主因：主线程热点是原生属性 getter 和数据库查询。
- JSON 序列化、请求体复制、对象驻留和垃圾回收仍可能放大后续卡顿。
- 修复后仍需同场景采样确认持续阻塞已消除。单次 `allNotebooks()`、关系 getter、对象转换、JSON 序列化和原生请求体复制均无法被 JavaScript 定时器抢占；不能保证所有 getter 热点消失或任意分片严格低于 50 ms。

## 回归证据与限制（2026-09-10）

`node tests/sync-check.js` 在修复前报错：`sync must yield before database collection`，实际数据库访问次数 1，预期 0。测试加载真实 `main.js`，模拟原生 getter、定时器和异步网络回调，不执行替代同步算法。

修复后，20,434 条笔记加一个文档的场景通过：关系每学习集只取一次，每个所需笔记字段只读一次，第一批在扫描全部笔记前发送，批次上限 500。每 getter 固定计入 0.1 ms 的模拟时钟下，最长收集分片为 8.8 ms。该数值仅验证预算与让出机制，不是 MarginNote 实测加速比，也不能代替 Core Data、内存和服务端正确性验收。

生命周期回归覆盖收集中停用/重置/断开、请求晚返回、重连、配置心跳晚返回、防重入、失败恢复、空库和大量链接。1.1.3 安装包已在原问题 MarginNote 环境实测，未再出现此前的长时间卡顿；尚未提供修复后采样、三周期内存趋势和真实服务端逐字段核对数据结果，因此这些项目仍保留为后续复测项。
